# pygrametl parallel ETL: threads or processes, chosen by the GIL

Benchmarks of pygrametl's example ETL program (from the 2011 paper *Easy and Effective
Parallel Programmable ETL*) on CPython 3.14 and 3.15, with and without the GIL, using
PostgreSQL and psycopg 3. pygrametl itself was modified so that its parallel constructs can
run on **threads** (for free-threaded CPython) as well as on processes.

## 2. The thread version of pygrametl

pygrametl's parallel constructs (`Decoupled*`, `ProcessSource`, the shared connection) always
used `multiprocessing` on CPython. They now run on processes or on threads, decided like this:

1. **Jython is unchanged.** It keeps using the original `jythonmultiprocessing.py`, which is back to the 2.9 file.
2. **CPython gets its own thread module,** `pygrametl/threadmultiprocessing.py`, with thread based stand-ins for `Process`, `Queue`, `JoinableQueue` and `Value`.
3. **The choice is made the first time a parallel construct is used,** by the environment variable `PYGRAMETL_PARALLEL`:
   - `auto` (the default): threads if the GIL is off, processes if it is on;
   - `threads`: always threads;
   - `processes`: always processes;
   - any other value raises a `ValueError`.

The GIL itself is set on the command line with `-X gil=0` (off) or `-X gil=1` (on). On a
free-threaded build that gives these combinations:

| `PYGRAMETL_PARALLEL` | `-X gil=0` | `-X gil=1` |
|---|---|---|
| not set (auto) | threads | processes |
| `threads` | threads, GIL off | threads, GIL on |
| `processes` | processes, GIL off | processes, GIL on |

A regular build always has the GIL on (and rejects `-X gil=0`), so auto gives processes there.
Python older than 3.13 has no GIL switch and also gets processes.

**Why the choice is made at first use and not at import:** a C extension can turn the GIL on
or off when it is imported. psycopg2 turns it on (so a "free-threaded" run silently loses its
threads); psycopg 3 leaves it off. Deciding late means the check sees the final state.

| File | Change |
|---|---|
| `threadmultiprocessing.py` (new) | Thread based `Process`, `Queue`, `JoinableQueue` and `Value` |
| `parallel.py` | `multiprocessing` is now a stand-in object that picks threads or processes on first use (`_usethreads()` reads `PYGRAMETL_PARALLEL` and `sys._is_gil_enabled()`). In thread mode a failing worker halts the program: `threadexitfunction` flushes `stderr` and calls `os._exit(1)`, and `_setthreadexcepthook()` installs a `threading.excepthook` that calls pygrametl's own hook. Without these, a crashing worker thread dies silently and the program hangs |
| `datasources.py` | `ProcessSource` and `DynamicForEachSource` take their queue and process from `pygrametl.parallel`; `import sqlite3` stays outside the Jython check, otherwise `SQLTransformingSource` breaks |
| `jythonmultiprocessing.py` | Unchanged |

**psycopg 3.** Importing psycopg 3 does not turn the GIL back on, so no flag is needed to keep
it off. It has no prebuilt wheel for the free-threaded build, so `psycopg[c]` is built from
source there (it needs `libpq-dev` and `build-essential`). The pure-Python fallback, plain
`psycopg`, needs no compiler but was about 40% slower in a bare-loop test (run in a one-core sandbox, not on the benchmark machine). The two benchmark
scripts were ported to psycopg 3 (`pygrametl1_pg3.py`, `pygrametl2_pg3.py`): `import psycopg`,
`psycopg.connect(...)`, and a bulk loader that uses `cursor.copy()` instead of `copy_expert`.

**Checks run on the benchmark machine:**
- `-X gil=0` selects `pygrametl.threadmultiprocessing`, and `-X gil=1` selects `multiprocessing`.
- With psycopg 3 the threads backend is selected whether psycopg or pygrametl is imported first, and the GIL stays off.
- A crashing worker prints its traceback and exits with code 1 instead of hanging.
- Every benchmark run below loaded 599,059 page versions and 5,000,000 facts.

## 3. How the runs were made

`bench.py` resets the tables, runs the program once, and prints wall-clock time, user and
system CPU time, "PostgreSQL time" (`pg_stat_database.active_time`) and the rows loaded. Each
command below runs a version 3 times, from the `run` folder with the venv active. Paste each as
one line.

**Regular build** (`.venv314-pg3` or `.venv315.pg3`), no flags:
```bash
for i in 1 2 3; do echo "=== sequential, run $i of 3 ==="; python ../bench.py python ../pygrametl1_pg3.py; done
for i in 1 2 3; do echo "=== multiprocessing, run $i of 3 ==="; python ../bench.py python ../pygrametl2_pg3.py; done
```

**Free-threaded build** (`.venv314t-pg3` or `.venv315t-pg3`):
```bash
for i in 1 2 3; do echo "=== sequential, run $i of 3 ==="; python ../bench.py python -X gil=0 ../pygrametl1_pg3.py; done
for i in 1 2 3; do echo "=== processes, GIL on, run $i of 3 ==="; PYGRAMETL_PARALLEL=processes python ../bench.py python -X gil=1 ../pygrametl2_pg3.py; done
for i in 1 2 3; do echo "=== processes, GIL off, run $i of 3 ==="; PYGRAMETL_PARALLEL=processes python ../bench.py python -X gil=0 ../pygrametl2_pg3.py; done
for i in 1 2 3; do echo "=== threads, GIL on, run $i of 3 ==="; PYGRAMETL_PARALLEL=threads python ../bench.py python -X gil=1 ../pygrametl2_pg3.py; done
for i in 1 2 3; do echo "=== threads, GIL off, run $i of 3 ==="; PYGRAMETL_PARALLEL=threads python ../bench.py python -X gil=0 ../pygrametl2_pg3.py; done
```

The sequential block was run again at the end of each build, as a check for drift. To keep a
copy of the output, add `2>&1 | tee -a results.txt` after the final `done`.

## 5. What the tables show

- **Threads with the GIL off only match sequential.** 201.4 s against 202.2 s on 3.14t, and 201.8 s against 198.3 s on 3.15t (differences of −0.4% and +1.7%, within noise), at about 2.2 times the CPU. No parallel version beats sequential.
- **Processes are 22 to 27% slower than sequential,** at about 3.1 to 3.3 times the CPU, on every build and both Python versions.
- **The GIL decides whether threads work.** With it off, threads are about 31% faster than with it on, and they are 18% faster than processes using 31% less CPU. With the GIL on they use exactly one core (0.99 and 0.98) and are 16 to 18% slower than processes.
- **The GIL matters little for processes:** GIL off is about 1.5% faster (4 s), consistently in every run pair, mostly from lower system time. Threads versus processes should therefore follow the GIL, which is what the `auto` setting does.
- **The free-threaded build costs 6 to 8% in speed** for sequential code (3.14: 7.5%, 3.15: 6.2%). The fastest configuration overall is sequential on the regular build (186.7 s on 3.15; 188.0 s on 3.14).
- **3.15 behaves like 3.14.** Ratios to the sequential run on the same build differ by 1 to 6 percentage points, and the times in seconds by 0 to 2.3%, which is within the drift seen between sessions.
- **PostgreSQL time is about 26 s for sequential,** against about 50 s with psycopg2 in earlier tests. Results with psycopg 3 are not comparable with psycopg2 results.

## 6. Notes and limits

- **One machine,** a laptop under WSL2. Compare configurations within one table or session. Earlier sessions drifted by 3 to 7% with no change to the code.
- **The harness prints page and fact counts, not the error total.** After a threaded run, check that it is 26,862,851 with `psql -h localhost -U chr -d chr -c "select sum(errors) from pygrametlexa.testresults"`.
- **The choice of threads or processes is made once,** at first use. If a C extension imported afterwards turns the GIL on, the program stays on threads with the GIL on, which is slower. No warning is given for that case.
- **A recorded limit of the design:** every database statement still goes through one shared connection, one at a time. This is intentional (it keeps the load in one transaction) and is why threads only match sequential.
